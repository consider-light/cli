## 一、完成的功能

### 1.1 配置驱动与启动校验

- 用一份 JSON 描述全部探测目标，字段包括 `name`、`type`、`address`、`expected_status`、`contains`、`retry_count`；当前配置有 9 个目标，覆盖 HTTP 与 TCP 两类。
- 缺省值在加载阶段补齐：`expected_status` 未填时按 200 处理。
- 启动前完成全部校验：地址格式（HTTP 用 `url.Parse` + scheme 白名单，TCP 用 `net.SplitHostPort`）、端口 1–65535、超时为正数、`type` 必须在已注册协议内。
- **一次报出全部问题**，而不是遇到第一个错误就退出；错误信息带目标序号与字段名，改一轮就能改完。

### 1.2 两类真实探测

| 类型 | 判定依据 | 说明 |
|---|---|---|
| HTTP | 状态码等于 `expected_status`，可选校验正文包含指定字符串 | 失败也保留已拿到的状态码，便于区分"连不上"与"连上了但返回不对" |
| TCP | `net.DialTimeout` 能建立连接 | 只验端口可达，不发业务数据 |

### 1.3 并发调度

- 一个目标一条 goroutine，不用 Worker Pool。IO 密集型任务，9 个目标就应该同时起跑。
- 结果 channel 的容量等于目标数，所有任务同时发送也不会互相阻塞。
- channel 的关闭只发生在收尾 goroutine，条件是 `WaitGroup` 归零；任务本身绝不 close，因为它不知道别人是否跑完。
- 实测：10 个目标并发执行总耗时 1.00 秒；若改为串行，仅每个目标 1 秒的固定延迟就要 10 秒。

### 1.4 超时与重试

- `-timeout` 是**单次尝试**的预算；`retry_count` 是额外重试次数，最终最多执行 `retry_count + 1` 次。
- 每次尝试都用 `context.WithTimeout` 新建预算，用完立即 `cancel`，各次尝试的超时互不影响。
- 是否需要重试只由**父 context** 决定：单次尝试超时说明目标慢，应该重试；父 context 被取消（如用户按 Ctrl+C）才终止。
- 每个目标执行前有项目要求的固定 1 秒延迟；延迟结束后立即检查父 context，如果此时程序已被取消，就不再发起网络请求，避免无意义的连接。

### 1.5 统计与报告

- 汇总区：总数、成功数、失败数、成功率、总耗时。
- 延迟统计区：样本数、最小、最大、平均、P50、P95，分位数用 nearest-rank 取实际观测值，不做插值。
- 延迟分布区：`[0,100ms)`、`[100,500ms)`、`[500,1000ms)`、`[1000,3000ms)`、`[3000ms,+inf)` 五个左闭右开区间。
- 最慢服务 TOP 3。
- **失败目标不参与延迟统计、分布与 TOP 3**，避免 DNS 失败、超时这类异常值把正常服务的延迟分布带偏。
- 表格按终端显示宽度对齐：一个汉字算 2 列，ASCII 算 1 列，中英混排不会错位。

### 1.6 命令行与退出码

- 参数只有三个：`-config`（配置路径）、`-timeout`（单次超时秒数）、`-v`（详细日志）。
- `-h` 打印用法后以 0 退出，不当作错误。
- 退出码：`0` 全部成功、`1` 存在失败目标、`2` 启动阶段错误（配置非法、参数非法等）。全项目只有 `main` 调 `os.Exit`。
- 入口在 `cmd/health-checker`，用 `go run ./cmd/health-checker` 运行；具体实现放在 `internal/entry`，`main` 只负责取退出码。

### 1.7 日志分层

- 默认只输出运行信息，报告仍然完整。
- 加 `-v` 后逐个目标输出 `RUNNING` / `RETRY` / `SUCCESS` / `FAILED`，能看到开始时间、第几次尝试、最终结果。
- 日志接口定义在 `scheduler`（消费方）而不是 `logger`，`logger` 只负责实现，依赖方向单向。

### 1.8 运行日志落盘

- 每次运行结束，在**当前工作目录**生成一份日志文件，文件名 `monitor-log-YYYYMMDDHHMMSS.log`，时间戳取本次运行的开始时刻，连续跑两次不会互相覆盖。
- 文件内容与终端一致：运行头部（开始时间、配置文件、单次超时）+ 运行日志 + 完整报告。终端上看到什么，文件里就有什么。
- 终端多打印一行 `[INFO] 日志文件: monitor-log-....log` 告知落点；这一行只给终端看，不写进文件，避免文件自我引用。
- 日志文件是附加产物，创建失败（目录不可写等）时降级为仅终端输出，只在 stderr 打一条 `[WARN]`，探测照常完成、退出码不变。
- 实现上由 `internal/logfile` 负责命名与创建，`app` 用 `io.MultiWriter(stdout, logFile)` 让日志与报告同时写往两处，因此不需要改 `logger` 和 `reporter`。

### 1.9 测试

- 14 个包（其中 11 个有测试用例），测试代码 3355 行，生产代码 1900 行。
- 单元测试覆盖配置校验、探测器、调度并发、重试路径、统计口径、表格对齐、日志文件命名与降级。
- 集成测试编译真实二进制、用 `os/exec` 跑完整流程，覆盖退出码、输出结构、日志文件生成。
- `go test ./...` 与 `go test -race ./...` 全部通过。

## 二、开发中遇到的问题与解决


1.两种类型请求如何设计 后续功能如何好扩展 
 解决方案 ：利用策略模式来解决 让策略层面对不同目标探测选择不同的策略方法（http tcp） 这样解除了耦合 也复用了代码 后续也可以更好地扩展

 2.github总是失败 
 解决方案 ：加入临时http代理 走我自己的梯子 就可以成功了

 3.重试的逻辑问题 外部超时时间已经到了 内部重试应该如何结束和开始
 解决方案 ：让外部做决定 假如外部没有抛出异常 就让内部重试进行 反之内部直接结束
